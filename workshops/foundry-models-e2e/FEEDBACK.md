# Workshop Feedback

## General

- **Progress granularity:** `.progress.json` should track completed sub-steps (e.g., `"00.1"`, `"00.2"`) alongside top-level steps, and each note entry should record the sub-step number plus a one-line outcome for fast review.

- **Always give the learner the command to run — never run it for them.** Every script execution should be framed as an explicit learner action with a code block they copy-paste, a description of what to watch for, and a "you should see…" confirmation prompt. The facilitating agent should narrate what the script does, then stop and wait. Running scripts on behalf of the learner removes the hands-on moment and breaks the learner-centric flow.

## Step 8 — Portal review

- **`s05_run_eval.py` can't log results to the Foundry portal — SDK incompatibility.** The `azure-ai-evaluation` SDK's `azure_ai_project` portal logging uses the Azure ML workspace API (`Microsoft.MachineLearningServices/workspaces`). New Foundry projects provisioned via `Microsoft.CognitiveServices` are *not* AML workspaces and return HTTP 404. Results must be read from the local `eval_results_<label>.json` file. The Step 8 portal review for evaluations should be changed to use the **Foundry portal's built-in eval runner** (upload the JSONL dataset + run from the portal UI) as the primary path, with the SDK harness positioned as the local/CI path. Add a note in Step 5 and Step 8 explaining this distinction.

## Step 7 — Multi-model agent v3

- **`carmen-trace.json` has a dead placeholder image URL.** The `image_url` field was `https://example.invalid/...` which causes a 400 error from the vision model. Fix: set `"image_url": null` so the vision OCR step is gracefully skipped (it's gated by `if image_url:` in the agent). Add an explicit note in the step: *"The sample trace has no image. If you want to exercise the vision branch, replace `image_url` with a public URL or base64 data URI of a receipt photo."*

## Step 0 — Setup

## Step 6 — Fine-tune

- **Deploy the fine-tuned model using the Developer SKU, not GlobalStandard.** When deploying from the Fine-tuning → Deploy dialog, select **Developer** as the deployment type. This provisions a temporary endpoint (auto-deleted after 24 hours) at lower cost — ideal for the workshop's eval-and-verify step before committing to a production deployment. The step instructions and CLI command should specify `--sku-name Developer` and note that learners should upgrade to GlobalStandard only if they want the deployment to persist beyond testing.

- **Policy-base quality is 0.47, not 0.28 as the workshop expects.** The `policy-mini-base` deployment (gpt-4.1-mini) already scores 0.47 on the 35-row policy slice — the base model has improved since the workshop was authored. The step still makes sense (there is a gap to close toward 0.94), but the "before" number in the chart, the narrative ("close the 0.28 gap"), and the troubleshoot table should be updated to use ~0.47 as the realistic baseline.
- **Baseline model family mismatch.** The workshop was likely authored against an older model (e.g. gpt-4o or earlier). All four deployments now use the gpt-4.1 series (gpt-4.1, gpt-4.1-mini, gpt-4.1-nano), which is stronger across the board. All expected baseline numbers throughout the workshop (quality, latency, cost, token counts) should be re-benchmarked against gpt-4.1 series and the scorecards updated accordingly.
- **Missing wait-time warning and portal exploration sub-step.** After `python s06_finetune_policy.py` is launched, add a clearly-boxed callout (e.g. `> ⏱ This job typically takes 30–90 minutes`) so learners know not to wait at the terminal. Then add a guided portal exploration sub-step to fill the time: (1) go to **Build → Data** tab — see the uploaded train/val files listed with file IDs and sizes; (2) go to **Build → Fine-tuning** tab — find the running job, click into it to see epoch-by-epoch training loss, hyperparameters, and estimated completion time. This turns the wait into a learning moment instead of dead time.
- **Add portal monitoring + Copilot analysis sub-step during FT wait.** While the fine-tune job runs, add a guided sub-step: (1) Go to **Build → Fine-tuning** → click the running job → open the **Metrics** tab; (2) take a screenshot of the training/validation loss curves once a few epochs have completed; (3) paste the screenshot into Copilot chat and ask *"Analyze this fine-tuning loss curve — is training converging well, is there evidence of overfitting, and should I change the number of epochs?"* This turns dead wait time into a real ML skills moment and introduces learners to using Copilot as an ML co-pilot, not just a code assistant.
- **Codespaces sleep resilience.** The fine-tune job runs entirely in Azure — a Codespace going to sleep won't cancel it. Add an explicit note: *"Codespaces may go to sleep during this wait — that's fine. The job keeps running in the cloud. Copy the job ID from the console output before leaving. If your terminal session is lost, you can resume by pasting the job ID into Copilot and asking it to poll the job and continue from where you left off."* The script should also print the job ID prominently (e.g. `SAVE THIS JOB ID: <id>`) so learners know to copy it.

## Step 5 — Evaluations

- **Rate limit hit during curated eval.** `s05_run_eval.py` uses `planner-gpt41` as both the agent and the LLM judge, firing 20+20 calls in rapid succession. The setup script provisions `planner-gpt41` at only 10K TPM GlobalStandard, which is insufficient. Recommend: bump `planner-gpt41` to at least 50K TPM before running evals, or add retry-with-backoff logic in `s05_run_eval.py`. The setup script (`s00_setup.sh`) should note this and offer an eval-mode capacity option.
- **`s06_finetune_policy.py` used wrong base model (`gpt-4.1` instead of `gpt-4.1-mini`).** The workshop narrative is "bake policy knowledge into the cheap model so the frontier model never has to answer policy questions." Using `gpt-4.1` as the FT base defeats that purpose — the fine-tuned model would still cost frontier pricing. Fix: set `BASE_MODEL = "gpt-4.1-mini"` in the script.
- **24 training examples insufficient to move quality.** With gpt-4.1-mini already at 0.47 on the policy slice, 24 FT examples produced no measurable quality gain (FT result: 0.46). The workshop's 0.94 target assumed a weaker base model and more training data. Recommend expanding `policy-ft-train.jsonl` to at least 80–100 examples covering edge cases and adversarial policy traps for the fine-tune story to land. Alternatively, re-frame the expected outcome as "specialisation + cost reduction" rather than a dramatic quality jump, and update scorecard targets accordingly.
- **Make distillation the conceptual centrepiece of Step 6, not a footnote.** The step should open with a clear two-sentence definition before any code: *"Knowledge distillation is the practice of using a large, expensive model (the teacher) to generate high-quality training labels, then fine-tuning a small, cheap model (the student) to replicate that quality. After distillation, the teacher is retired from the inference path entirely — you pay frontier cost once at training time, never again at runtime."* Then show the cost arithmetic concretely: if gpt-4.1 costs $5/1M tokens and gpt-4.1-mini costs $0.40/1M tokens, distillation delivers a 12× inference cost reduction for the policy task with no quality loss after fine-tuning. The workshop should include a callout box titled *"Why distillation beats prompting"* that explains: (1) the student internalises domain knowledge so no retrieval or long system prompt is needed; (2) latency drops because the student is smaller and the context is shorter; (3) cost drops proportionally to the size gap between teacher and student. Learners hit rate limits as soon as they run any eval (Step 5) or synthetic generation (Step 4). The script should default to at least **50K TPM** for all deployments so learners never have to manually bump quota mid-workshop. The current 10K is only safe for single-call demos.

## Step 2 — Baseline agent in VS Code

- **s02_baseline_agent.py: model returns prose instead of JSON.** The system prompt asks for a JSON itinerary but gpt-4.1 responds in natural language prose after completing tool calls. Fix applied: after the tool-call loop ends, append a user message containing "json" then make one additional `responses.create` call with `text={"format": {"type": "json_object"}}` to force a clean JSON final answer. Note: the `json_object` format requires the word "json" to appear in the input messages — the extra user message satisfies this constraint.
- **s02_baseline_agent.py: `booking_status` and `policy_notes` type mismatch.** The model may return `booking_status` as a plain string (not a dict) and `policy_notes` as a string (not a list). The display code assumed dicts/lists and crashed. Fix applied: type-check both fields before rendering.
- **Missing 2.4: check the Monitor tab in the portal.** After running `s02_baseline_agent.py`, add a sub-step directing learners to the portal **Monitor** tab (Build → Deployments → `planner-gpt41` → Monitor, or the project-level Monitor view) to verify the calls landed: total requests, token consumption, cost, and any failures. The step should reference `assets/01-home.png` and `assets/02-models.png` to orient learners visually.
